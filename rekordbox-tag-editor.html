This case study covers a personal project to build a mobile app to help DJs tag and organize music, tackling a notoriously tedious part of the job.

Role
Solo concept, 2026. Designed and vibe-coded the prototype end to end.
Status
A working mobile prototype of the tagging flow. Speculative, not shipped, and not yet tested with other DJs.
Skills
Background

An industry stuck with one tool

Nearly every CDJ in every club and festival booth is a Pioneer CDJ. That hardware lock-in is what makes Rekordbox the standard, not the software itself. DJs use it because it's what the hardware speaks, not because they'd choose it on its merits.

Rekordbox is also widely known for being buggy, and Pioneer's parent company keeps prioritizing new physical hardware releases over fixing the app. That means real, long-standing pain points in the software just sit there, with no real pressure on the company to fix them.

Problem

Tagging is crucial, but tedious

Tags aren't just genre labels. For most DJs they encode the vibe of a track, where it might sit in a set, and overlapping subgenres, all of it personal and subjective to how that DJ hears and mixes music. That's exactly why an AI can't just auto-tag a library: it's not a lookup problem, it's a matter of taste.

An interaction that hurts to use

Rekordbox's tagging UI is a dense grid of dropdowns and checkboxes, track by track. It's slow enough that DJs online describe genuine repetitive strain injury from sitting through it, and there's no fix coming soon.

No way to do it away from a desk

Rekordbox only exists as a desktop app, so tagging only ever happens sitting at a computer. There's no way to chip away at a backlog on a train, backstage, or anywhere else dead time shows up.

The result is a library that keeps growing faster than it gets organized, because the only tool for organizing it demands a desk and a lot of patience.

Approach

A mobile companion, not a rebuilt Rekordbox

I scoped this narrowly on purpose: a phone-first companion focused only on tagging and library metadata, syncing against your existing Rekordbox library rather than trying to replace it.

Weighing desktop, mobile, and both

Before committing to a mobile companion, I weighed it against a desktop-only fix and against building both. Here's how the three options compared.

How it'd work Tagging efficiency Ease of setup Build effort
Desktop only A local app running on the same machine as Rekordbox, reading and writing directly through pyrekordbox and python-vlc. Fastest per track by a wide margin, but total volume capped by how often you sit down for a session. Easiest. One native app, nothing networked. Moderate. Needs the pyrekordbox integration built out (reading and writing tags reliably against Rekordbox's own, partly encrypted format) plus a real keyboard-driven bulk-tagging UI, multi-select, playback controls, shortcut handling. No networking or security work required, which keeps it lighter than the other two, but a polished native UI from scratch is still genuine, nontrivial work, not a small one.
Mobile only A backend service plus a lightweight web app, tagging via touch and swipe. Slower per track, but more frequent sessions can push total volume higher. Artist suggestions narrow some of the per-track gap. A packaged background service, no Docker needed, plus Tailscale on the phone. Moderate. Streaming and tag-writing were both estimated at close to an evening's work once scoped. The real remaining effort is the tagging interaction itself, gesture conflicts and the multi-directional design are still open, though the riskiest unknowns, background audio surviving a lock screen, the interaction feeling responsive, are already tested rather than assumed.
Desktop + Mobile A shared backend, plus a native bulk-tagging editor at the desk and a touch-driven web app on the phone, all bundled into one installer. Highest total throughput, additive rather than a compromise between the other two. About the same as mobile only, one installer covers both. Highest, and genuinely so now, not just a small add-on. This is the full scope of both builds combined, the pyrekordbox integration and native editor from the desktop column, plus the backend and web app from the mobile column, plus the packaging work to bundle it all into a single native installer.
Solution

What the concept looks like

A tag editor built for your thumb

Instead of Rekordbox's dense dropdown grid, tagging happens through scrollable rows of chips sized for one hand: vibe, set placement, and subgenre, tap to assign, swipe to move to the next track.

Tag anywhere, sync when you're back

Tagging works fully offline, so a commute or the dead time before a set becomes time spent on the backlog instead of lost. Everything queues up and syncs back into the Rekordbox library the next time you're at your laptop.

Mobile web had its own tax

Building this as a mobile web app instead of native surfaced problems the interaction design never anticipated: layouts that wouldn't reliably respect the viewport, chip rows that jumped or reflowed mid-gesture, transitions that stayed janky under real touch input, and autosuggested tags that lagged behind typing.

None of that was a UX flaw to redesign around. It's the cost of building for reach on the browser instead of native performance, and it ate a real share of the build time.

Two tools that don't talk to each other

The workflow itself split across two disconnected tools: prompting the live build and testing real interactions in Claude Code, then switching to Claude Design to sketch a new interaction quickly and dropping the result back into Claude Code as a screenshot with a prompt describing what to build.

That back-and-forth worked, but it was manual every time. The two tools not sharing context directly was the actual friction, more than either one individually.

Outcomes

A working prototype, not a launch

This exists today as a working mobile prototype, built to pressure-test whether the tagging interaction itself could actually be faster on a phone. It hasn't shipped, and it hasn't been tested with other DJs yet.

The open question that matters most is syncing cleanly back into Rekordbox's own library format without corrupting anyone's crates. That's the next thing to solve before this could go in front of anyone else.

Reflections

Designing around a platform that won't fix itself

This wasn't just a UX problem. Rekordbox's owner has no real incentive to fix tagging when its hardware sells regardless, so any real fix has to work around the platform rather than through it. That framing shaped the whole scope: a companion, not a pitch to replace anything.

Building a working prototype instead of static screens forced real interaction decisions much earlier than a mockup would have. Chip sizing, gesture direction, and how offline queuing should feel all got settled by actually using it, not by describing it.

The honest next step is putting this in front of other DJs who've felt this exact pain. Until then, it's a strong hunch backed by a prototype, not a validated solution.
